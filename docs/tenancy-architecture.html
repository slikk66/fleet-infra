Multi-tenancy architecture (hardway)

Two layers (platform vs tenant) and three independent isolation boundaries around every tenant, plus GPU partitioning. Source of truth is docs/tenancy-architecture.md. Blue = platform (cluster-admin), green = tenant (confined), red = secret/denial.

0. The big picture — three boundaries

A tenant is boxed in on three independent axes — separate mechanisms, enforced by different parts of the system. Don't conflate them.

1. The two-layer GitOps control plane

The platform tenants Kustomization installs every guardrail plus the tenant's own GitRepository + Kustomization. team-b is an exact mirror.

2. Boundary ① — Control plane (RBAC + impersonation)

Flux's kustomize-controller is itself cluster-admin; impersonation makes it apply a tenant's manifests as the tenant SA, so the apiserver enforces the tenant's RBAC.

3. Boundary ② — Data plane (NetworkPolicy)

RBAC never sees a packet. The pod network is flat by default; a per-tenant NetworkPolicy (standard networking.k8s.io, enforced by Cilium) allows ingress only from the same namespace. A drop shows as a timeout, not "refused". CiliumNetworkPolicy is a superset CRD, not required here.

4. Boundary ③ — Consumption (ResourceQuota + LimitRange)

ResourceQuota caps namespace totals (cpu/mem/pods + GPU via requests.<resource>). LimitRange is the required companion: a quota on requests.cpu rejects pods that omit a cpu request, so it supplies defaults + min/max. Over-quota pods are Forbidden at admission.

5. GPU isolation — MIG (spatial partitioning)

MIG carves one physical GPU into hardware-isolated slices (vs time-slicing = temporal, no isolation). The device-plugin advertises each slice as an extended resource (from the topology's otherDevices); pods request a slice like any resource; ResourceQuota caps them per tenant.
